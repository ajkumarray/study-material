# Phase 7 — Security: Interview Q&A

⭐ = asked constantly.

**Q: Authentication vs authorization?** ⭐⭐
Authentication verifies *who you are* — checking credentials (a username/password pair at login, or in this project's case, validating a signed JWT's claims on every subsequent request). A successful authentication produces an `Authentication` object stored in Spring Security's `SecurityContext` for the current request. Authorization decides *what you're allowed to do*, given an already-established identity — checking roles/authorities against the rules attached to the requested resource. Authorization strictly follows authentication: Spring Security only evaluates authorization rules once it knows (or has explicitly decided it doesn't need to know, for a public endpoint) who's making the request. `expense-api`'s `SecurityConfig` demonstrates both: `JwtAuthFilter` handles authentication (parses and validates the bearer token, populates the `SecurityContext`), and `.authorizeHttpRequests(...)` handles authorization (`anyRequest().authenticated()` — a coarse rule requiring *some* valid identity, without yet checking specific roles).

**Q: How does Spring Security work at a high level?** ⭐
It's a chain of servlet filters sitting in front of the application — every request passes through this chain before it ever reaches a `@RestController`. Filters in the chain handle authentication (verify identity, populate the `SecurityContext`) and authorization (check the now-known identity against access rules) in sequence. You configure the chain's behavior by defining a `SecurityFilterChain` bean, as `SecurityConfig.filterChain(HttpSecurity http)` does — declaring which URL patterns are public (`permitAll()`), which require authentication (`anyRequest().authenticated()`), the session policy (stateless, in this project), and any custom filters to insert (`JwtAuthFilter`, added *before* Spring Security's own standard username/password filter via `addFilterBefore`).

*Follow-up: What happens with zero security configuration at all, just the starter on the classpath?* Spring Security defaults to secure-by-default: every endpoint requires authentication, with a single in-memory user and a randomly generated password printed to the console log at startup — a deliberately inconvenient default that forces you to write your own `SecurityFilterChain` rather than accidentally shipping an unsecured app.

**Q: How should passwords be stored?** ⭐⭐
Hashed with a slow, salted, adaptive algorithm — BCrypt (or Argon2/scrypt) — never plaintext, and never a fast general-purpose hash like MD5 or SHA-1/SHA-256 alone, which are designed to be *fast*, the opposite of what you want for password hashing (fast hashing makes brute-force attacks against a leaked password database cheap). `expense-api` wires `BCryptPasswordEncoder` as its `PasswordEncoder` bean; `AuthService.register` calls `encoder.encode(rawPassword)` and stores only the resulting hash on `AppUser`, never the raw password. BCrypt automatically salts each hash (embedding a fresh random salt in the output string on every call), so identical passwords produce different stored hashes and precomputed rainbow-table attacks don't work. Verification never decrypts — a `PasswordEncoder` is one-way; login re-hashes the submitted password using the same salt embedded in the stored hash and compares the two hash values, which is exactly what happens under the hood when `AuthService.login` delegates to `authManager.authenticate(...)`.

**Q: What is JWT and why use it for APIs?** ⭐⭐
A JSON Web Token is a signed, self-contained token — `header.payload.signature`, each part base64url-encoded — carrying claims (in this project: username as `subject`, an issued-at timestamp, an expiration timestamp). The client sends it on every request as `Authorization: Bearer <token>`; the server validates the signature (proving it wasn't tampered with, since a valid signature can only be produced by someone holding the signing secret) and checks the expiry, and — if both check out — trusts the claims without needing to consult any server-side session store. Because no session state is stored anywhere, any server instance can independently validate any token, which is exactly what lets a JWT-secured API scale horizontally with zero coordination between instances. This makes it the natural fit for stateless REST APIs and single-page/mobile clients that a session cookie doesn't suit well.

*Follow-up: Is the JWT payload encrypted?* No — only encoded (base64url), not encrypted. Anyone who has the token can decode and read its payload without the signing secret. The signature is what guarantees *integrity* (can't be tampered with undetected), not *confidentiality*. This is precisely why nothing sensitive (passwords, PII beyond a username) belongs in a JWT payload — `expense-api`'s token payload deliberately carries only a username and timing claims.

**Q: Session-based vs token-based auth?** ⭐
Session-based: the server creates and stores session state (in memory or a shared store) after login, and the client holds a session identifier, typically in a cookie, sent automatically on subsequent requests. It's inherently stateful — scaling to multiple server instances needs either sticky sessions (routing a client's requests back to the same instance) or a shared session store, and revocation is trivial (delete the server-side session). Token-based (JWT): the token is self-contained and the server verifies it independently on every request with no stored state at all — scales freely across any number of instances with zero coordination, but revoking a single token before its natural expiry is hard, precisely because there's no server-side record of "issued tokens" to delete from. REST APIs, especially ones serving decoupled frontends (SPAs, mobile apps), typically favor the stateless token approach — which is exactly the model `expense-api` implements and the model its planned frontend integration is built around.

**Q: What's a downside of JWT and how do you mitigate it?**
The core downside is that a valid, unexpired JWT can't be easily revoked — once issued, the server has no record of it to invalidate; it remains "valid" by the pure signature/expiry check until it naturally expires, even if the user logs out, their account is disabled, or their session should be terminated immediately for security reasons. Standard mitigations: keep the access token's lifetime short (this project's `app.jwt.expiration-ms` is set to one hour) so any compromised or stale token's window of usefulness is naturally limited, paired in a fuller implementation with a separate, longer-lived refresh-token flow that lets a client obtain a new short-lived access token without re-authenticating from scratch. For urgent revocation needs (a compromised token, immediate account suspension), a server-side denylist of specific revoked token identifiers is the usual fallback, accepting the small added state that reintroduces.

**Q: What is CSRF and does it apply to a stateless JWT API?**
CSRF (Cross-Site Request Forgery) tricks a victim's browser into submitting an authenticated request to a site the victim is logged into, exploiting the fact that browsers automatically attach stored cookies to any request to that domain — the attacker's page never sees the victim's session cookie, but can still cause an authenticated request to fire using it. It's fundamentally a cookie/session-based-auth problem. `expense-api` authenticates via an `Authorization: Bearer <token>` header, which a browser does *not* attach automatically the way it does cookies — a malicious page has no way to make the victim's browser include that header on a forged request — so CSRF protection doesn't defend against anything relevant here, and `SecurityConfig` explicitly disables it (`.csrf(csrf -> csrf.disable())`). A cookie/session-based application, by contrast, should generally leave CSRF protection enabled.

**Q: How do you authorize at the method level?**
`@EnableMethodSecurity` on a configuration class turns on method-level authorization checks, then `@PreAuthorize("hasRole('ADMIN')")` (or `@PostAuthorize`, or the simpler, older `@Secured`) on individual service/controller methods enforces fine-grained rules beyond what URL-pattern matching in `SecurityConfig.authorizeHttpRequests(...)` can express. `@PreAuthorize` evaluates its SpEL expression *before* the method runs and throws `AccessDeniedException` (mapped to 403) if it's false; `@PostAuthorize` evaluates after the method returns, useful when the decision needs the method's own return value (for example, checking that a returned expense actually belongs to the requesting user, not just any authenticated user). `expense-api` doesn't currently have a role-restricted endpoint using this — both defined roles (`USER`, `ADMIN`) aren't yet differentiated by access — but it's the standard next step the moment an application's authorization model needs finer granularity than "authenticated or not" per URL prefix.

**Q: Why does Spring Security default to 403 for an unauthenticated request, and why does this project override it?**
Spring Security's historical default treats any request denied by the authorization layer — for any reason, including simply having no credentials at all — as `403 Forbidden`. For a REST API, that conflates two situations a client needs to handle very differently: "you presented no or invalid credentials, please authenticate" (`401 Unauthorized`) versus "you're authenticated, but you don't have permission for this" (`403 Forbidden`). `expense-api` fixes this by registering a custom `AuthenticationEntryPoint` — invoked specifically for unauthenticated (not merely unauthorized) requests — that explicitly returns 401. `SecurityJwtIntegrationTest.protectedEndpointRequiresToken` asserts exactly this behavior: `GET /api/expenses` with no `Authorization` header returns `401`, not the framework's raw default of 403.

*Follow-up: Give a concrete example of when this project's API would (or should) return 403 instead.* If a valid, authenticated request presented a legitimate token for a `ROLE_USER` account but attempted to hit an endpoint gated with `@PreAuthorize("hasRole('ADMIN')")`, that request has already succeeded at authentication — the server knows exactly who's asking — but authorization correctly denies it, and Spring Security's default `AccessDeniedException` handling maps that specific case to 403. The custom `AuthenticationEntryPoint` this project adds only affects the *unauthenticated* case; it leaves the authenticated-but-forbidden case at its correct default of 403.

**Q: Walk through what happens, filter by filter, when a client calls `GET /api/expenses` with a valid bearer token.**
The request enters Spring Security's filter chain. `JwtAuthFilter` (inserted via `addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)`) runs first among the custom pieces: it reads the `Authorization` header, confirms it starts with `Bearer `, strips the prefix, and calls `jwt.isValid(token)` — which internally parses the token, verifies its HMAC signature against the server's configured secret key, and checks that its expiration timestamp is still in the future. If valid, it extracts the username claim, calls `userDetailsService.loadUserByUsername(username)` (backed by `AppUserDetailsService`, which looks the user up via `UserRepository.findByUsername` and builds a Spring Security `UserDetails` carrying the stored BCrypt hash and role), and constructs a `UsernamePasswordAuthenticationToken` with that principal and its authorities, storing it in `SecurityContextHolder`. The filter then always calls `chain.doFilter(...)`, regardless of whether authentication succeeded — it never itself rejects the request. Later, the authorization layer (`anyRequest().authenticated()`) inspects the now-populated (or still-empty) `SecurityContext`: since a valid `Authentication` is present, the request is allowed through to `ExpenseController.list()`, which calls the real `ExpenseService`. If the token had instead been missing, expired, or tampered with, `SecurityContext` would remain empty at that authorization check, and the custom `AuthenticationEntryPoint` would send back 401 instead of letting the request reach the controller at all.
