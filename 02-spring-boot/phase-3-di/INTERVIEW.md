# Phase 3 — Dependency Injection: Interview Q&A

⭐ = asked constantly.

**Q: What is a Spring bean?**
An object whose creation, dependency wiring, and lifecycle are managed by the Spring IoC container rather than by application code calling `new`. You declare a class as a bean either implicitly, via a stereotype annotation (`@Component`, `@Service`, `@Repository`, `@RestController`) picked up by component scanning, or explicitly, via a `@Bean` method in a `@Configuration` class. Once registered, the container is responsible for resolving that bean's own dependencies, injecting them, and — for the default singleton scope — handing out the same shared instance to every class that depends on it.

**Q: `@Component` vs `@Service` vs `@Repository` vs `@Controller`?** ⭐
All four register a class as a bean via component scanning; they differ in semantic intent, and one of them also adds real behavior. `@Component` is the generic base stereotype. `@Service` marks the business-logic layer — purely documentation, no extra runtime behavior versus plain `@Component`. `@Repository` marks the persistence layer and *does* add behavior: Spring wraps repository beans so that low-level, technology-specific persistence exceptions get translated into Spring's unified, unchecked `DataAccessException` hierarchy — meaning calling code can catch a consistent exception type regardless of whether the underlying technology is JDBC or JPA. `@Controller`/`@RestController` mark the web layer, handling HTTP requests. Using the right stereotype for each layer is largely about readability and tooling (IDEs, architecture diagrams, and other developers can infer a class's role from its annotation and package alone) — but `@Repository`'s exception translation is a genuine functional difference worth calling out specifically.

*Follow-up: Do Spring Data repository interfaces need `@Repository`?* No — `JpaRepository`-based interfaces like `ExpenseRepository` get the exception-translation behavior automatically as part of the Spring Data infrastructure, without you adding `@Repository` yourself.

**Q: Which injection type is best and why?** ⭐⭐
Constructor injection — used throughout `expense-api` (`ExpenseService(ExpenseRepository repository)`, `ExpenseController(ExpenseService service)`, `JwtService(@Value(...) String secret, ...)`, all constructor-injected). The reasons stack up: dependencies can be declared `final`, so the object is guaranteed fully and correctly initialized the instant it exists — there's no window where it's half-wired. It's trivially unit-testable with zero Spring involvement — `new ExpenseService(mockRepository)` in a plain JUnit test works exactly because the dependency is a constructor parameter, not a private field set by reflection. Circular dependencies (bean A needs B, B needs A) are caught immediately at application startup with a clear `BeanCurrentlyInCreationException`, rather than surfacing later as a mysterious runtime null. And since Spring 4.3, a class with exactly one constructor doesn't even need `@Autowired` on it — Spring infers it automatically, which is why none of the constructors in `expense-api` carry that annotation.

Field injection (`@Autowired` on a private field) is discouraged because the dependency is invisible from the class's public API — you can't construct the object with a mock in a plain unit test without reflection tricks, and a misconfigured context can leave the field `null`, surfacing as a `NullPointerException` only when it's first used, rather than at startup. Setter injection sits in between: it allows post-construction reconfiguration (occasionally useful for genuinely optional dependencies) but permits a temporarily invalid, half-wired object between construction and the setter call.

*Follow-up: What actually happens at startup if you have a real circular dependency with constructor injection?* Spring detects it while trying to build the object graph and throws a `BeanCurrentlyInCreationException` describing the cycle — the app fails to start. (With field/setter injection, Spring can sometimes paper over certain circular dependencies by injecting a partially-constructed bean, which is a subtler and arguably worse outcome — constructor injection forces you to actually break the cycle in your design.)

**Q: What is the default bean scope? What are the implications?** ⭐
Singleton — exactly one instance of a given bean exists per Spring container, shared across the entire application, including every concurrent HTTP request. The direct implication is that singleton beans must be stateless or fully thread-safe, since many requests may be executing the same instance's methods simultaneously. `ExpenseService` demonstrates this correctly: its only field is `private final ExpenseRepository repository`, set once at construction and never mutated afterward — no per-request mutable state, so sharing one instance concurrently is safe. If a `@Service` instead held a mutable instance field that requests wrote to, that would be a data race, because there's only one instance for the whole running application to share.

Other scopes exist for cases needing per-injection or per-request instances: `prototype` (a new instance every time the bean is requested/injected — rare in a typical layered app), and the web-specific `request`/`session` scopes (one instance per HTTP request or session).

**Q: `@Autowired` — how does resolution work? What if there are multiple candidates?**
Spring resolves dependencies by type first. If exactly one bean of the required type exists, it's injected without any extra configuration. If more than one bean of the same type exists (e.g., two implementations of the same interface), Spring needs disambiguation: `@Qualifier("beanName")` at the injection point names the exact bean to use, or `@Primary` on one of the candidate beans marks it as the default winner whenever no qualifier is specified elsewhere. Without either, startup fails with `NoUniqueBeanDefinitionException` — a fail-fast error rather than an arbitrary silent pick. For dependencies that may legitimately be absent, `@Autowired(required = false)`, wrapping the parameter type in `Optional<T>`, or injecting Spring's `ObjectProvider<T>` all express "this may not exist" without failing startup at all.

**Q: `@Value` vs `@ConfigurationProperties`?**
`@Value("${key}")` injects a single property and supports Spring Expression Language for defaults or light computation — this is what `expense-api`'s `JwtService` constructor uses for `app.jwt.secret` and `app.jwt.expiration-ms`, two standalone values. `@ConfigurationProperties(prefix = "...")` binds an entire nested configuration section onto a typed class in one shot — better once a config group grows past one or two properties, since it keeps related settings colocated in a single class, supports relaxed binding (kebab-case YAML keys like `expiration-ms` map to camelCase Java fields `expirationMs`), and can be validated as a unit with `@Validated` plus Bean Validation annotations on the properties class itself. As a rule of thumb: reach for `@Value` for one-off values, and `@ConfigurationProperties` the moment you have a cohesive block of related settings (a datasource, a third-party API's credentials, feature flags).

**Q: What are Spring profiles?** ⭐
Named labels used to conditionally activate beans or configuration for a specific environment — dev, test, prod — from one built artifact, without recompiling. `expense-api`'s `DataSeeder` is annotated `@Profile("!test")`, meaning that whole `@Configuration` class (and the `CommandLineRunner` bean it defines, which seeds a demo user and sample expenses) is excluded whenever the active profile is `test`. `SecurityJwtIntegrationTest` activates that profile via `@ActiveProfiles("test")`, so its `@SpringBootTest` context boots with a guaranteed-clean, unseeded database — a concrete example of profiles keeping test behavior isolated from "convenience" startup code meant for local development. In a deployed app, the more common pattern layers `application-dev.yml`/`application-prod.yml` on top of the base `application.yml`, activated by `spring.profiles.active`, to vary things like the datasource URL or log level per environment.

*Follow-up: What's the config precedence order if the same property is set in multiple places?* Roughly, from highest to lowest priority: command-line arguments, environment variables, profile-specific `application-{profile}.yml`, the base `application.yml`, then any hardcoded default (e.g., the fallback after the colon in `${JWT_SECRET:default-value}`). Higher-precedence sources override lower ones — this is exactly what lets the same JAR pick up a real secret from an environment variable in production while quietly falling back to a safe local default in dev.

**Q: How does `@Bean` differ from `@Component`?**
`@Component` (and its specializations) is class-level, auto-detected via component scanning — you annotate a class you own, and Spring finds and registers it automatically as long as it's under the scanned package tree. `@Bean` is method-level, inside a `@Configuration` class, and explicitly constructs and returns the object to be registered — used when you don't own the class being registered (a third-party library type with no annotation you can add) or when constructing it needs logic beyond a bare no-arg or simple constructor call. `expense-api`'s `DataSeeder` is the clearest example: its `seed(...)` `@Bean` method takes three other injected beans as parameters and returns a `CommandLineRunner` lambda that uses them to populate demo data — there's no single class you could slap `@Component` on to achieve that; the bean *is* the return value of a method with real logic in it. `SecurityConfig` does the same for `PasswordEncoder` (`new BCryptPasswordEncoder()`) and `AuthenticationManager` (pulled from Spring Security's `AuthenticationConfiguration`) — both are types the application configures rather than classes it defines itself.
