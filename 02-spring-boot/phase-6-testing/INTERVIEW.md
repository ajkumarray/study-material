# Phase 6 — Testing: Interview Q&A

⭐ = asked constantly.

**Q: `@SpringBootTest` vs test slices?** ⭐⭐
`@SpringBootTest` boots the entire, real `ApplicationContext` — every `@Service`, `@Repository`, security filter, and configuration class wired together exactly as production would be. It's high-fidelity but slow, because it pays the full startup cost of the application. Test slices load only the layer under test: `@WebMvcTest(controllers = X.class)` loads just the web layer (the named controller, MVC infrastructure, JSON conversion, validation, `@RestControllerAdvice`) with everything else — services, repositories — mocked via `@MockBean`/`@MockitoBean`; `@DataJpaTest` loads just the JPA layer against an in-memory database, wrapping each test in a rolled-back transaction. `expense-api`'s suite deliberately uses all three: `@WebMvcTest` for `ExpenseControllerTest` (fast, isolated controller behavior), `@DataJpaTest` for `ExpenseRepositoryTest` (fast, proves derived queries generate correct SQL), and `@SpringBootTest` for `SecurityJwtIntegrationTest` (slower, but the JWT flow genuinely needs the real filter chain end to end). The rule of thumb: default to the narrowest slice that can actually verify what you're testing, and reserve full-context tests for things that specifically require real cross-layer wiring.

**Q: What is MockMvc?** ⭐
A test utility that dispatches simulated HTTP requests through the real Spring MVC stack — real controller methods, real JSON serialization, real validation, real exception handling — without starting an actual network server or opening a real socket. `mvc.perform(get("/api/expenses/99")).andExpect(status().isNotFound()).andExpect(jsonPath("$.detail").value("expense not found: 99"))` (from `ExpenseControllerTest`) builds a fake GET request, dispatches it through the MVC machinery, and asserts both the resulting HTTP status and a specific field inside the JSON response body via a JSONPath expression. It's the standard pairing with `@WebMvcTest` for fast controller tests, and also works fine under `@SpringBootTest` when a test needs the full real stack, as `SecurityJwtIntegrationTest` demonstrates.

**Q: `@Mock` vs `@MockBean`/`@MockitoBean`?** ⭐
`@Mock` is plain Mockito — it creates a mock object with zero Spring involvement, useful in a bare unit test that constructs the class under test directly with `new` and no Spring context at all. `@MockBean` (Spring Boot ≤ 3.3) / `@MockitoBean` (3.4+) does something extra: it creates a Mockito mock **and** installs it into the Spring test context, replacing whatever real bean of that type would otherwise have been wired there. `ExpenseControllerTest` uses `@MockBean ExpenseService service` inside a `@WebMvcTest` — the controller under test still gets a real, Spring-managed `ExpenseService` reference injected into it exactly as production would, except that reference now points at a fully controllable mock instead of a real service backed by a real database. Use the Spring-aware variant whenever the class under test is itself wired up through a Spring context (slice or full); use plain `@Mock` when you're bypassing Spring entirely.

**Q: How do you test the persistence layer?**
`@DataJpaTest` — it configures just the JPA/Hibernate layer against an in-memory database and auto-rolls back each test method, so tests stay isolated from one another regardless of order. Its real purpose, specifically for Spring Data, is proving that *derived query methods* — which have no hand-written implementation, only a method name Spring Data parses into a query — actually generate correct SQL. `ExpenseRepositoryTest.derivedQueryFindByCategory` saves two `FOOD` expenses and one `RENT` expense, then asserts `repo.findByCategory(Category.FOOD)` returns exactly two results and `repo.findByCategory(Category.RENT)` returns exactly one — a concrete proof that the generated `WHERE category = ?` query behaves correctly, not merely that it compiles.

*Follow-up: How do you achieve higher fidelity than H2 for these tests?* Testcontainers (below) — H2 is fast and convenient but not identical in behavior to a real production database engine.

**Q: What is Testcontainers and why use it?** ⭐
A library that spins up a real instance of an actual infrastructure dependency — Postgres, Kafka, Redis, whatever the app actually uses in production — inside a Docker container, scoped to a single test run, and tears it down automatically afterward. Paired with `@SpringBootTest` and `@DynamicPropertySource` (which injects the container's real, dynamically-assigned connection details into the Spring context's configuration before startup), it lets integration tests run against the *actual* database engine rather than a stand-in like H2 — catching dialect-specific SQL behavior, real constraint enforcement, and connection-pool behavior that an in-memory substitute might not faithfully reproduce. It requires Docker in the test execution environment, which is why it isn't wired into this project's current suite, but it's the professional standard for trustworthy integration testing in real Spring Boot codebases.

**Q: Describe the testing pyramid for a Spring app.**
At the base, many fast tests: plain unit tests of services constructed with `new` plus mocked dependencies (zero Spring involvement at all — the direct payoff of constructor injection), and fast slice tests (`@WebMvcTest`, `@DataJpaTest`) that load only one architectural layer. In the middle, fewer, slower integration tests: `@SpringBootTest`, optionally paired with Testcontainers for full infrastructure fidelity, verifying that layers actually wire together correctly end to end — `SecurityJwtIntegrationTest` sits here, since proving the whole JWT flow (register → token → authenticated request → rejection of a bad token) genuinely requires the real filter chain. At the top, the fewest, slowest tests: full end-to-end tests against a deployed system. The shape optimizes for fast feedback on most changes while still retaining genuine confidence that the whole system actually works together.

**Q: How do you unit-test a service without Spring?**
Because services in this project use constructor injection exclusively (Phase 3.2), you can simply call `new ExpenseService(mockRepository)` directly in a plain JUnit test, with `mockRepository` a bare Mockito mock (`mock(ExpenseRepository.class)` or `@Mock`) — no `@SpringBootTest`, no context startup, no Spring annotations involved at all. This runs in milliseconds and is the fastest possible tier of the testing pyramid. It's directly enabled by the constructor-injection discipline: a class relying on field injection (`@Autowired` on a private field) can't be constructed this way at all, because there's no constructor parameter to hand a mock to — you'd need either a real Spring context or reflection tricks just to populate the field. This is the single most concrete, interview-ready justification for "why constructor injection" beyond the abstract design-principle argument.

*Follow-up: If `ExpenseService` had a second dependency added later, what would break in a test written this way?* Only the test's `new ExpenseService(...)` call site — you'd add the new mock parameter to the constructor call. Because the dependency is explicit in the constructor signature, the compiler itself forces every caller (including every test) to be updated the moment a new dependency is added, rather than a field-injected dependency silently defaulting to `null` in a test that never knew it needed to be mocked.

**Q: Why does `ExpenseControllerTest` exclude `SecurityConfig`/`JwtAuthFilter` and set `addFilters = false`, while `SecurityJwtIntegrationTest` doesn't?**
`ExpenseControllerTest` is a `@WebMvcTest` whose entire purpose is verifying `ExpenseController`'s own HTTP behavior — correct status codes, correct JSON shape, correct validation-error responses — completely independent of authentication. Leaving the real security filter chain active in that slice would mean every request in that test class needs a valid token just to reach the controller at all, entangling two unrelated concerns (does the endpoint behave correctly vs. is the endpoint properly protected) inside the same test class, and making failures harder to diagnose (a broken assertion could mean either "the controller logic is wrong" or "the security config accidentally changed"). So the slice explicitly excludes `SecurityConfig`/`JwtAuthFilter` from its component scan and disables MockMvc's security filters (`@AutoConfigureMockMvc(addFilters = false)`), isolating the controller entirely. `SecurityJwtIntegrationTest`, by contrast, is a `@SpringBootTest` whose entire purpose *is* verifying the real security flow — no token gets 401, a valid token from registration authenticates a subsequent request, a garbage token is rejected — so it deliberately keeps the real filter chain active and asserts against it directly. Splitting these concerns into two test classes, each with an appropriately scoped context, is the more maintainable pattern versus one bloated test class trying to verify everything at once.
