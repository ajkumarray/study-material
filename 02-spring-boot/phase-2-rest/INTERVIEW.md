# Phase 2 — REST APIs: Interview Q&A

⭐ = asked constantly.

**Q: What makes an API RESTful?** ⭐
Resources are identified by URIs and treated as nouns (`/api/expenses`, `/api/expenses/{id}`), and actions on them are expressed through the standard HTTP methods (GET reads, POST creates, PUT replaces, PATCH partially updates, DELETE removes) rather than being baked into the URL (`/getExpense`). Requests are stateless — each one carries everything needed to process it (in `expense-api`, a bearer token per request, no server-side session), so any server instance can handle any request, which is what lets the API scale horizontally without sticky sessions. There's a uniform interface: consistent conventions for status codes and representations across every resource. And representations (typically JSON) are decoupled from internal storage — the client talks to DTOs, not database rows.

The strictest academic definition of REST also requires HATEOAS — every response includes hypermedia links describing what the client can do next, so a client theoretically never needs to hardcode a URL. Almost no production "REST API," including this one, actually does this; most are more accurately "HTTP+JSON APIs that follow REST conventions." It's worth naming that distinction explicitly if asked, since conflating the two is a common gap.

*Follow-up: Is statelessness violated by using sessions or cookies for auth?* Yes — a server-side session (even backed by a cookie) means the server must remember per-client state between requests, which breaks strict statelessness and complicates horizontal scaling (you need sticky sessions or a shared session store). That's exactly why `expense-api` uses stateless JWT bearer tokens instead (Phase 7.3): each request is self-authenticating.

**Q: `@Controller` vs `@RestController`?** ⭐
`@RestController` is `@Controller` plus `@ResponseBody` applied to every handler method. `@Controller` alone is Spring MVC's traditional annotation, where a handler's return value (typically a `String`) is resolved to a *view name*, which a view resolver (e.g., Thymeleaf) then renders into HTML for a server-rendered page. Adding `@ResponseBody` changes that: instead of resolving a view, Spring writes the return value directly to the HTTP response body using an `HttpMessageConverter` — Jackson serializes it to JSON. `@RestController` bundles both, so every method in a class like `ExpenseController` returns data (JSON), never a view. REST APIs always use `@RestController`; `@Controller` is for server-rendered pages.

**Q: `@PathVariable` vs `@RequestParam`?** ⭐
`@PathVariable` extracts a value embedded directly in the URL path — it identifies *which* resource you mean (`/api/expenses/{id}` → `@PathVariable long id`). It's a structural part of the URL. `@RequestParam` extracts a value from the query string (`?days=7`) — it's used for optional filters, sorting, or pagination options that modify how a resource collection is fetched, and it naturally supports defaults (`@RequestParam(defaultValue = "7") int days`, used by `GET /api/expenses/recent`). A good rule of thumb: if omitting the value would still make sense as a valid, different request, it's a query param; if the value identifies the specific resource, it's a path variable.

**Q: PUT vs PATCH vs POST, and what does idempotency actually mean?** ⭐
POST creates a new resource — it is not idempotent: sending the same POST twice creates two separate resources (two `id`s). PUT replaces a resource wholesale at a known URI — it is idempotent: sending the same PUT twice leaves the resource in the same final state as sending it once (the second call just re-writes the same values). PATCH partially updates a resource; whether it's idempotent depends on the semantics of the patch operation (setting a field to a fixed value is idempotent; incrementing a counter by the patch is not).

Idempotency specifically means: *repeating the identical request produces the same end-state as making it once* — it does not mean "returns the same response every time." A repeated DELETE is idempotent even though the first call might return `204 No Content` and the second `404 Not Found`, because the underlying state ("this resource doesn't exist") is unchanged between the two calls.

*Follow-up: Why does idempotency matter operationally?* It's what makes safe automatic retries possible. If a client times out waiting for a response to a PUT and doesn't know whether the request landed, it can safely retry — an idempotent operation guarantees the retry won't double-apply the change. Retrying a non-idempotent POST blindly could create a duplicate resource.

**Q: Why use DTOs instead of returning entities directly?** ⭐⭐
Several concrete reasons, all visible in `expense-api`. First, decoupling: the entity `Expense` maps to the `expense` database table; `ExpenseResponse` maps to the JSON the API promises clients. They can evolve independently — renaming a database column only requires updating `ExpenseResponse.from(...)`, not breaking every client overnight. Second, security/least exposure: `CreateExpenseRequest` deliberately has no `id` field, so a client cannot set or overwrite the server-assigned primary key by including one in the JSON body; more generally, a DTO only exposes exactly the fields you choose, never an entity's full internal shape (audit columns, internal foreign keys, etc.). Third, it avoids JPA-proxy serialization pitfalls — Jackson trying to serialize a lazily-loaded Hibernate proxy directly can throw `LazyInitializationException` or serialize unwanted nested data; converting to a plain DTO sidesteps that entirely. Fourth, it gives validation a clean home: Bean Validation annotations live on the request DTO (`@NotBlank`, `@Positive`, `@PastOrPresent` on `CreateExpenseRequest`), so bad input is rejected at the boundary before it reaches the service or database.

The pattern used throughout is: `CreateExpenseRequest` (validated inbound) → service builds/mutates the `Expense` entity → `ExpenseResponse.from(entity)` (curated outbound). Returning entities directly is one of the most commonly flagged issues in Spring code review, because it silently welds your public API contract to your database schema.

**Q: What status code for create / delete / not found / validation failure?**
Create (`POST /api/expenses`) → `201 Created`, with a `Location` header pointing at the new resource's URL (`ResponseEntity.created(uri).body(...)` in `ExpenseController.create`). Successful delete with nothing to return → `204 No Content` (`ResponseEntity.noContent().build()`). A resource that doesn't exist (fetched by id, or deleted by id) → `404 Not Found`, produced by the `ExpenseNotFoundException` → `@ExceptionHandler` mapping in `GlobalExceptionHandler` (Phase 5.2). Failed Bean Validation on a request body → `400 Bad Request`, via the `MethodArgumentNotValidException` handler. Getting these right is part of the contract itself — a client can branch on status code alone without parsing the response body.

*Follow-up: When would you use 422 instead of 400?* `422 Unprocessable Entity` is sometimes used to distinguish "syntactically valid JSON, but semantically wrong" (e.g., a business-rule violation) from `400 Bad Request` ("malformed/missing required data"). Many APIs (including Spring's default validation handling) don't bother with the distinction and use 400 for both; either is defensible as long as it's applied consistently.

**Q: How does Spring convert objects to/from JSON?**
Via Jackson, auto-configured by `spring-boot-starter-web` because it's on the classpath. `@RequestBody CreateExpenseRequest req` on a controller parameter tells Spring to read the raw JSON request body and deserialize it into a `CreateExpenseRequest` instance using Jackson (matching JSON field names to record component names by default). Conversely, returning any object from a `@RestController` method (or wrapping it in `ResponseEntity`) serializes it back to JSON via the same `HttpMessageConverter` mechanism. Records work particularly well here because Jackson can use the canonical constructor directly — no extra `@JsonCreator` annotations needed for a simple case like `ExpenseResponse`.

**Q: How do you handle a collection response and content negotiation?**
Return a `List<Dto>` (as `ExpenseController.list()` does: `service.all().stream().map(ExpenseResponse::from).toList()`), and Jackson serializes it to a JSON array automatically — no wrapping needed. Content negotiation is the mechanism Spring MVC uses to decide *which* representation format to produce, based primarily on the request's `Accept` header; with just the web starter, JSON via Jackson is effectively the only configured format, so it's the default regardless. If you added `spring-boot-starter-web` with an XML converter on the classpath (e.g., Jackson's XML module), the same endpoint could serve XML or JSON depending on what the client requests.
