# Phase 4 — Spring Data JPA: Interview Q&A

⭐ = asked constantly.

**Q: What does Spring Data JPA give you over plain JPA/Hibernate?** ⭐⭐
Plain JPA/Hibernate still requires you to write a DAO/repository class per entity, manually calling `EntityManager.persist()`, `find()`, building `TypedQuery`s or `CriteriaQuery`s for anything beyond a primary-key lookup. Spring Data JPA removes that layer entirely: declare an interface extending `JpaRepository<Entity, Id>` and get a full CRUD implementation — `save`, `findById`, `findAll`, `deleteById`, `count`, plus pagination and sorting — generated at runtime as a dynamic proxy, with zero implementation code. On top of that, **derived query methods** turn a method name like `findByCategory` into a working `WHERE category = ?` query just by parsing the name against the entity's fields, and `@Query` covers anything too complex for a method name. In `expense-api`, this collapses what would be roughly a 120-line hand-written JDBC repository (the Java capstone's `JdbcExpenseRepository`) down to a single-line interface: `public interface ExpenseRepository extends JpaRepository<Expense, Long> { }`.

**Q: How do derived query methods work?** ⭐
At application startup, Spring Data parses each repository method name against the entity's known properties. `findByCategoryAndAmountGreaterThan` is tokenized into `findBy` + `Category` (a property of `Expense`) + `And` + `Amount` (another property) + `GreaterThan` (a comparison keyword), and translated into `WHERE category = ? AND amount > ?`. Recognized keywords cover the common set of conditions and modifiers: `And`, `Or`, `Between`, `LessThan`/`GreaterThan`(`Equal`), `Like`, `In`, `IsNull`, `OrderBy...Asc/Desc`, `Top`/`First` (for limiting results), and `exists`/`count` prefixes that change the return type instead of adding a `WHERE` condition. `ExpenseRepository`'s `findByCategory(Category)`, `findByAmountGreaterThan(BigDecimal)`, and `findBySpentOnGreaterThanEqualOrderBySpentOnDesc(LocalDate)` are all real examples — no implementation exists anywhere; `ExpenseRepositoryTest` (a `@DataJpaTest`) proves the generated SQL actually behaves correctly by saving known rows and asserting the derived methods return exactly the expected subset.

*Follow-up: What happens if you typo a property name in a derived method, like `findByCatgory`?* Spring Data validates method names against the entity's actual properties at application startup (it has to, in order to build the query), so a typo fails immediately with a clear startup error — not a runtime SQL exception discovered later in production. This fail-fast behavior is one of the underrated benefits of the derived-query approach over raw SQL strings.

**Q: When do you use `@Query`?**
When a query's condition logic would make the derived method name unreadably long, when you need to return a projection/DTO shape directly instead of a full entity, or when you need explicit control over exactly what SQL executes for performance tuning. `@Query` takes JPQL by default — an object-oriented query language operating on entity classes and their fields (`SELECT e FROM Expense e WHERE e.category = :category`), portable across database vendors because Hibernate translates it to the target dialect's SQL. Setting `nativeQuery = true` switches to raw, vendor-specific SQL for cases JPQL can't express (window functions, database-specific syntax), trading portability for full control.

**Q: What does `@Transactional` do and how?** ⭐⭐
It declaratively wraps a method's execution in a database transaction: begin before the method runs, commit if it completes normally, roll back if an unchecked exception (`RuntimeException`/`Error`) propagates out. Spring implements this through **AOP proxying** — at startup, the bean is wrapped in a dynamically generated proxy, and every call made *through that proxy* is intercepted to open/commit/roll back the transaction around the real method call. `ExpenseService` is `@Transactional` at the class level (every public method transactional by default) with `@Transactional(readOnly = true)` overriding that for pure read methods (`all()`, `byId()`, `recent()`) — the read-only flag is an optimization hint letting Hibernate skip dirty-checking for that transaction.

The gotcha interviewers specifically probe for: `@Transactional` only applies to calls made *through the proxy* — a method inside the same class calling another `@Transactional` method on `this` directly (self-invocation) bypasses the proxy entirely, so no transaction boundary is applied to that inner call. This is a genuinely common production bug, usually surfacing as "why didn't this rollback?" The other gotcha: rollback only happens automatically on unchecked exceptions by default — a checked exception thrown from a `@Transactional` method does *not* trigger a rollback unless you explicitly configure `rollbackFor = SomeCheckedException.class`.

*Follow-up: How would you deliberately trigger a rollback for a checked exception?* Either declare the checked exception type in `@Transactional(rollbackFor = MyCheckedException.class)`, or — more commonly in practice — avoid checked exceptions in the transactional boundary altogether by wrapping/rethrowing as an unchecked exception, which is the prevailing style in modern Spring codebases (matching `ExpenseNotFoundException` and `UsernameTakenException` in this project, both unchecked).

**Q: What is the N+1 select problem and how do you fix it?** ⭐⭐
Loading a list of N parent entities and then triggering an *additional* query per parent to fetch a lazily-loaded association — 1 query for the parents plus N queries for their associations, N+1 total round trips, instead of one well-joined query. It typically shows up when iterating a `List<Parent>` and calling a getter on each item's lazy `@OneToMany`/`@ManyToOne` collection inside the loop; each access silently fires its own `SELECT`. The fix is to eagerly fetch the association in the *same* query up front, either with `JOIN FETCH` in a JPQL `@Query`, or with Spring Data's `@EntityGraph` annotation on a repository method — both tell Hibernate to include the association in the original query via a SQL join, collapsing N+1 round trips into one. In practice, you detect it by watching the SQL log (`spring.jpa.show-sql: true`, set in `expense-api`'s `application.yml`) explode into a burst of near-identical queries when a collection is iterated.

**Q: Why can't a JPA entity be a Java record?** ⭐
Hibernate instantiates entities via reflection using a **no-arg constructor**, then populates fields afterward — and needs to be able to generate **lazy-loading proxy subclasses** of the entity class for associations marked `FetchType.LAZY`. A Java `record` is implicitly `final` (can't be subclassed — breaks proxy generation), has no no-arg constructor, and its fields are `final`, set exactly once in the canonical constructor (breaks Hibernate's instantiate-then-populate strategy and dirty checking, which relies on being able to mutate managed entity state). `expense-api`'s `Expense` entity is deliberately a mutable class with a `protected` no-arg constructor for exactly this reason, while its DTOs (`CreateExpenseRequest`, `ExpenseResponse`) *are* records — records are the right shape for the immutable, boundary-crossing DTO role, and the wrong shape for the mutable, reflection-populated, potentially-proxied entity role.

**Q: `FetchType` LAZY vs EAGER?**
`LAZY` defers loading an association until it's actually accessed — the default for collection-valued associations (`@OneToMany`, `@ManyToMany`) — which avoids over-fetching data you may never use, but is the direct cause of N+1 if accessed inside a loop, and can throw `LazyInitializationException` if accessed after the owning persistence context/transaction has already closed. `EAGER` loads the association immediately alongside its parent — the default for `@ManyToOne`/`@OneToOne` — simpler to reason about but risks loading more data than a given use case actually needs. Best practice for real applications: explicitly default every association to `LAZY`, and opt into eager loading per-query (via `JOIN FETCH`/`@EntityGraph`) only where that specific query genuinely needs the associated data.

**Q: `ddl-auto` settings — and production practice?**
`create`/`create-drop`/`update` have Hibernate inspect `@Entity` classes and generate/alter the database schema to match — convenient in dev (`expense-api` uses `update`, so the schema always tracks entity changes automatically) but dangerous against a real database, since Hibernate's inferred alterations can be destructive or unexpected as entities evolve. `validate` checks the entity mappings against the existing schema at startup and fails fast on any mismatch, but never modifies the schema itself. `none` disables schema management entirely. Production practice is `validate` (or `none`) paired with a versioned migration tool — Flyway or Liquibase — that owns the actual schema through reviewable, ordered migration scripts, rather than letting a framework infer DDL from Java class shape.

**Q: What is the persistence context / first-level cache?**
A per-transaction cache of every entity Hibernate has loaded or saved during that transaction. Looking up the same entity by id twice within one transaction returns the *same Java object instance* the second time, without issuing a redundant query — and it's this tracked-instance mechanism that also powers **dirty checking**: Hibernate keeps a snapshot of each managed entity's state as it entered the persistence context, compares it against the entity's current state at flush/commit time, and automatically issues an `UPDATE` for whatever changed — no explicit `save()` call required. This is why, inside a `@Transactional` method, mutating a managed entity's fields via its setters and simply letting the method return is enough to persist the change; `ExpenseService` doesn't demonstrate this directly today (its `delete`/`add` paths call the repository explicitly), but it's a fundamental JPA behavior worth being able to explain precisely, since it's one of the most commonly misunderstood aspects of the framework for developers coming from raw JDBC.
