# Phase 8 — Production: Interview Q&A

⭐ = asked constantly.

**Q: What is Spring Boot Actuator?** ⭐
A starter (`spring-boot-starter-actuator`) that exposes a set of ready-made operational HTTP endpoints for monitoring and managing a running application — `/actuator/health` (liveness/readiness), `/actuator/info` (build/app metadata), `/actuator/metrics` (JVM, HTTP, and datasource metrics, backed by Micrometer), plus others like `/env` and `/loggers` (change log levels live, without a restart) that aren't enabled by default. `expense-api` opts into exactly three via `management.endpoints.web.exposure.include: health,info,metrics` — deliberately not the full set, since several actuator endpoints (`/env`, `/beans`, `/mappings`) can leak sensitive internal configuration and shouldn't be exposed without careful access control. Health checks are what a load balancer or a Kubernetes liveness/readiness probe polls to decide whether to route traffic to an instance or restart it; metrics feed dashboards and alerting systems like Prometheus/Grafana. It's effectively the standardized "ops interface" every Spring Boot app gets for free.

*Follow-up: Why does `expense-api`'s `SecurityConfig` explicitly `permitAll()` `/actuator/health` but leave everything else requiring authentication?* A health-check probe (a load balancer, Kubernetes) has no way to present a JWT — it's an infrastructure component, not an authenticated user — so the endpoint has to be reachable with zero credentials for the whole health-check mechanism to function at all. Exposing only `health` publicly (not `metrics` or `info`, which could still be gated behind auth or a separate management port in a more hardened setup) is the deliberate minimal-exposure choice.

**Q: How do you configure an app differently per environment?** ⭐
Spring profiles: `application-{profile}.yml` files layered on top of the base `application.yml`, activated via `spring.profiles.active` (as a command-line arg, environment variable, or in config itself), varying things like datasource URLs, log levels, or which actuator endpoints are exposed per environment. Secrets specifically are never hardcoded or committed — they're injected via environment variables at deploy time, following the pattern `expense-api` uses for its JWT secret: `app.jwt.secret: ${JWT_SECRET:change-me-to-a-long-random-secret-at-least-32-bytes!!}`, where the real value comes from the `JWT_SECRET` environment variable in any real deployment, falling back to an obviously-fake local default otherwise. Configuration precedence (command-line args > env vars > profile-specific files > base `application.yml`) is what guarantees a deployment platform's injected environment variable always wins over whatever's baked into the packaged artifact — letting one built JAR run correctly, unmodified, across every environment.

**Q: What does `mvn package` produce for a Spring Boot app?**
An executable "fat JAR" (uber-JAR), built by the `spring-boot-maven-plugin` declared in `pom.xml` — it contains your compiled classes, every dependency, and the embedded servlet container (Tomcat), all nested inside one file that a custom Boot class loader knows how to run directly with `java -jar expense-api.jar`. Without that plugin, a plain Maven `package` would produce only a "thin" JAR of your own classes, requiring a separately assembled classpath to actually run. The fat JAR is self-contained and identical across every environment (local, CI, production) — no separate "prod build" step, no environment-specific artifact drift — and it's precisely what makes containerizing the app close to trivial: a Dockerfile just needs a JVM base image and a `COPY` of this one file.

*Follow-up: How is `mvn spring-boot:run` different from `mvn package` + `java -jar`?* `spring-boot:run` (from the same Boot Maven plugin) runs the application directly from source during development, without packaging a JAR at all — the fast everyday inner-loop command. `mvn package` produces the actual deployable artifact used everywhere downstream of a developer's machine — CI, staging, production.

**Q: How do virtual threads help a Spring Boot app?** ⭐
On Boot 3.2+ running Java 21+, setting `spring.threads.virtual.enabled=true` switches the embedded Tomcat's request-handling thread pool from OS ("platform") threads to JVM-managed virtual threads — one config line, zero code changes. The problem it solves: a traditional thread-per-request server ties up an expensive OS thread for the *entire* duration of a request, including time spent blocked on I/O (a database query, a downstream HTTP call) — and OS threads are costly enough (stack memory, OS scheduling overhead) that a server can realistically only run a few thousand concurrently, becoming the bottleneck under high concurrent load with slow I/O, well before CPU or memory limits are hit. Virtual threads are cheap enough to create millions of, and critically, when a virtual thread blocks on I/O, the JVM automatically unmounts it from its underlying OS thread — freeing that OS thread to service other virtual threads in the meantime — and remounts it once the I/O completes. Every existing blocking call already written in a codebase like `expense-api` (a synchronous `repository.findById(id)`, for instance) benefits automatically, with no code rewrite, because the JVM handles the efficient scheduling transparently underneath the exact same synchronous code.

*Follow-up: Why not just use Spring WebFlux/reactive programming instead?* WebFlux solves the same blocking-I/O-doesn't-scale problem, but via a fundamentally different, non-blocking programming model (`Mono`/`Flux`, callback-style composition) with a real learning curve and materially harder debugging (stack traces span asynchronous boundaries). Virtual threads deliver a large part of the same scalability benefit while letting the codebase keep its simple, synchronous, blocking style throughout — the payoff without the paradigm shift, which is why they've become the preferred default for many services that don't have WebFlux's more specialized streaming/backpressure requirements.

**Q: What are the three pillars of observability?**
Logs — discrete, timestamped events, often carrying free-text detail about exactly what happened at a specific point ("what happened in this one request/error"), handled via SLF4J + Logback. Metrics — aggregated numeric measurements over time (request counts, error rates, latency percentiles, JVM memory), collected through Micrometer (Spring's vendor-neutral metrics facade, exported to systems like Prometheus and visualized in Grafana) and exposed directly by Actuator's `/actuator/metrics` — answers "how is the system behaving in aggregate." Traces — the path one specific request takes across services/components, with timing recorded at each hop, via Micrometer Tracing/OpenTelemetry — answers "where exactly did time go for this one slow request," especially once a request fans out across multiple services, which a single-service app like `expense-api` doesn't yet need but would as soon as it started calling downstream services.

**Q: How do you add caching?**
`@EnableCaching` on a configuration class turns Spring's caching abstraction on, and `@Cacheable("cacheName")` on a method declares that its return value should be cached, keyed by the method's arguments — repeated calls with the same arguments return the cached value instead of re-executing the method body; `@CacheEvict` removes entries when underlying data changes. The actual storage is pluggable behind that same declarative API — a simple in-memory cache for a single instance, or a distributed cache like Redis (track 15) once multiple running instances need to share a consistent view of what's cached. `expense-api` doesn't use caching today (its query patterns are simple enough not to need it), but `ExpenseService.totalsByCategory()` — an aggregation that recomputes over every expense on each call — is exactly the shape of method that would benefit the moment it started being called frequently relative to how often the underlying expense data actually changes.

**Q: How would you containerize this app?**
Because it's already packaged as a self-contained executable fat JAR (Section 3 above), a minimal Dockerfile suffices: a JVM base image (`FROM eclipse-temurin:21-jre`), `COPY target/expense-api-*.jar app.jar`, `ENTRYPOINT ["java","-jar","/app.jar"]` — three lines, because the JAR already *is* the complete runnable application, embedded server included; Docker's only job is providing a JVM and copying one file in. Alternatively, `mvn spring-boot:build-image` (Cloud Native Buildpacks, bundled with the Boot Maven plugin) produces an optimized, layered container image directly from the Maven build, without hand-writing a Dockerfile at all — it separates dependencies, application code, and resources into distinct image layers, so a code-only change rebuilds and re-pushes a much smaller layer than a full image rebuild would. The full mechanics of both approaches, plus multi-stage builds and image size optimization, are covered in the Docker track.

**Q: What production concerns beyond correctness does a real deployment need to think about?**
Graceful shutdown — configuring the server to stop accepting *new* requests immediately on shutdown while giving in-flight requests a bounded grace period to finish, rather than abruptly severing active connections on every routine deployment or scale-down event. Connection pool tuning — Boot's auto-configured JPA/JDBC `DataSource` uses HikariCP by default, reusing a small, bounded set of already-open database connections rather than paying the cost of a fresh connection per request; pool size needs deliberate tuning against both the app's real concurrency and the target database's own connection limits, since too small a pool causes request queuing under load and too large a pool risks overwhelming the database or wasting memory on idle connections. `expense-api`'s current setup relies on HikariCP's sensible defaults, appropriate for its small H2 in-memory database, but a real production deployment against Postgres would tune `spring.datasource.hikari.*` deliberately. These are the categories of bugs that show up specifically in production under real load or real deployment cycles, even when an application's business logic and test suite are entirely correct — distinct from, and just as important as, functional correctness.
