# Phase 5 — Validation & Error Handling: Interview Q&A

⭐ = asked constantly.

**Q: How does validation work in Spring Boot?** ⭐
Through Bean Validation (the Jakarta Validation specification, implemented by Hibernate Validator, brought in via `spring-boot-starter-validation`). You annotate fields on a request DTO with constraint annotations — `expense-api`'s `CreateExpenseRequest` uses `@NotBlank` on `description`, `@NotNull` + `@Positive` on `amount`, `@NotNull` on `category`, and `@NotNull` + `@PastOrPresent` on `spentOn`. Putting `@Valid` on the corresponding `@RequestBody` controller parameter tells Spring MVC to run all of that DTO's constraints *before* the handler method body executes. If any constraint fails, Spring throws `MethodArgumentNotValidException` — the controller method (and the service layer behind it) never runs at all — and that exception is what a global exception handler maps to a `400 Bad Request`.

**Q: `@NotNull` vs `@NotEmpty` vs `@NotBlank`?** ⭐
`@NotNull` rejects only `null` — it works on any type, including non-string types like `BigDecimal` or `LocalDate` (used on `amount`, `category`, `spentOn` in `CreateExpenseRequest`). `@NotEmpty` rejects `null` *and* a zero-length string or empty collection, but a whitespace-only string (`"   "`) still passes it. `@NotBlank` is the strictest of the three — it rejects `null`, empty, *and* whitespace-only strings, since it trims before checking length — this is what's used on `description`, because an expense description of `"   "` is just as useless as an empty one. In strictness order: blank ⊂ empty ⊂ null-check, each one a stronger condition than the last, but only the string-oriented two (`NotEmpty`/`NotBlank`) make sense for text fields specifically.

**Q: How do you handle exceptions globally?** ⭐⭐
A `@RestControllerAdvice` class with one or more `@ExceptionHandler(SomeException.class)` methods, applied automatically across every `@RestController` in the app. `expense-api`'s `GlobalExceptionHandler` maps five distinct cases: `ExpenseNotFoundException` → 404, `MethodArgumentNotValidException` (thrown by failed `@Valid` checks) → 400 with a per-field `errors` map attached, `UsernameTakenException` → 409, `BadCredentialsException` (thrown by Spring Security's `AuthenticationManager` on a bad login) → 401, and a catch-all `Exception` → 500 with a generic, non-leaking message. Centralizing this in one class means controllers never need try/catch — `ExpenseController.get(id)` just calls `service.byId(id)` and lets `ExpenseNotFoundException` propagate; the advice class is solely responsible for translating it into the right HTTP response, and every controller in the app gets that same consistent error mapping for free.

*Follow-up: What order does Spring check `@ExceptionHandler` methods in if an exception could match more than one?* Spring picks the most specific matching handler — if you have a handler for a parent exception type and another for a subclass, the subclass-specific one wins for an instance of that subclass. If two handlers are equally specific for the actual thrown type, it's ambiguous and best avoided by keeping handler exception types non-overlapping, as `GlobalExceptionHandler` does (each handled type is a distinct, unrelated exception class, with `Exception.class` only as the final unambiguous catch-all).

**Q: `@ControllerAdvice` vs `@RestControllerAdvice`?**
`@RestControllerAdvice` is `@ControllerAdvice` plus `@ResponseBody` applied to every handler method in the class — exactly the same relationship as `@RestController` to `@Controller` (Phase 2). With plain `@ControllerAdvice`, a handler method's return value would be resolved as a view name; `@RestControllerAdvice` instead serializes it directly to the response body as JSON — the correct choice for a REST API, which is why `expense-api`'s `GlobalExceptionHandler` returns `ProblemDetail` objects directly and expects them serialized to JSON, not resolved as a view.

**Q: What is RFC 7807 / Problem Details?** ⭐
A standardized JSON shape for representing HTTP API errors, so clients can parse failures the same way regardless of which API they're talking to, instead of learning each API's bespoke error format. The core fields are `type` (a URI identifying the error category, `about:blank` when there's nothing more specific to link), `title` (a short human-readable summary, generally derived from the status), `status` (the numeric HTTP status code), and `detail` (a specific explanation of *this* particular failure). Spring's `ProblemDetail` class implements it directly — `ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage())` builds exactly this shape. It's also extensible: `GlobalExceptionHandler`'s validation handler calls `pd.setProperty("errors", fieldErrors)` to attach a custom `errors` map of `field → message` beyond RFC 7807's base fields, letting a client precisely highlight which form fields failed without breaking the standard contract for consumers that only understand the base fields.

**Q: Where should validation live — controller, service, or entity?**
Format/input validation belongs at the boundary — Bean Validation annotations on the request DTO plus `@Valid` in the controller, so malformed input is rejected fast with a `400` before touching business logic at all. That covers everything `CreateExpenseRequest`'s annotations check: required fields, positive amounts, non-future dates. Business-rule or cross-field validation that needs domain state — "is this username already taken" — doesn't fit as a single-field annotation and belongs in the service layer; `AuthService.register` explicitly calls `users.existsByUsername(username)` and throws `UsernameTakenException` before proceeding, precisely because that check requires a database lookup a DTO-level annotation can't perform. Entity-level constraints (`@Column(nullable = false, unique = true)` on `AppUser.username`) are the last line of defense at the database — they exist to guarantee correctness even under conditions the earlier layers can't fully prevent (e.g., a race between two concurrent registration requests both passing the service-layer uniqueness check before either commits). It's defense in depth: each layer exists for a different reason (fast UX at the edge, domain correctness in the middle, unconditional guarantee at the bottom), not redundant duplication.

**Q: Why not return stack traces or exception messages directly to clients?**
Two distinct reasons. Security: a stack trace or raw exception message can leak internal implementation details — class names, package layout, SQL fragments — information that helps an attacker understand the system's internals. UX: a raw `NullPointerException` message is meaningless to whoever is consuming the API and trying to fix their request. `GlobalExceptionHandler`'s catch-all `Exception` handler demonstrates the right pattern: it returns a generic `"unexpected error"` detail with no exception-specific text, while the real exception would be logged server-side for debugging (not shown to the client at all). Contrast that with the specific, expected exception handlers (`ExpenseNotFoundException`, `UsernameTakenException`), which *do* safely surface `ex.getMessage()` — because those messages are deliberately authored to be client-facing ("expense not found: 99", "username already taken: foo"), not raw internal diagnostics.

**Q: Default rollback behavior of `@Transactional` with exceptions?**
By default, a `@Transactional` method's transaction rolls back automatically on any unchecked exception (`RuntimeException`/`Error`) propagating out of it, and does *not* roll back on checked exceptions unless you explicitly configure `rollbackFor`. Both `ExpenseNotFoundException` and `UsernameTakenException` in this project are unchecked, so throwing either from inside a transactional service method rolls back any changes that method had already made earlier in its own execution — the whole method is one atomic unit, not just the line that threw.

This matters specifically in how it interacts with the exception-handling layer: the rollback decision is made at the `@Transactional` AOP proxy boundary, *before* the exception ever reaches `GlobalExceptionHandler` — by the time the advice class sees the exception and builds an HTTP response, any rollback has already happened. The two mechanisms are independent and compose in sequence: transaction management happens first (closer to the data layer), HTTP response translation happens second (at the web layer), and neither one is aware of or depends on the other's internal logic.

*Follow-up: If you wanted a specific checked exception to also trigger a rollback, how would you configure it?* `@Transactional(rollbackFor = MyCheckedException.class)` on the method (or class) — this explicitly extends the default rollback rule to cover that checked exception type as well, without needing to redesign it as unchecked.
