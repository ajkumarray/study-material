# Phase 5 — Component Patterns: Interview Q&A

⭐ = asked constantly.

**Q: What does "lifting state up" mean, and when would you do it?** ⭐⭐
It means moving state from wherever it's currently defined up to the closest common ancestor of every component that needs to read or change it, then passing it back down as props (for reading) and callback props (for requesting changes). You do it specifically when two or more **sibling** components need to share the same data — since siblings can't pass props directly to each other, the only place they can both reach is their shared parent. In `expense-web`, `ExpenseForm`, `Summary`, and `ExpenseList` are all siblings that each need some relationship to the same expense list, so that state lives in their common parent `App` (via the `useExpenses` hook), with each sibling receiving only the specific props it needs — `ExpenseForm` gets `onAdd`, `Summary` gets `expenses`, `ExpenseList` gets `expenses` and `onDelete`.

*Follow-up: what's the downside of lifting state too eagerly, even when it's not shared?* Over-lifting concentrates unrelated state in a single top-level component, which then re-renders (and potentially causes children to re-render) for changes that were never actually needed by more than one component — e.g., if `ExpenseForm`'s individual field values were lifted into `App` unnecessarily, every keystroke would re-render the entire `App` tree, including `Summary` and `ExpenseList`, for no benefit, instead of staying contained to `ExpenseForm` alone.

**Q: Explain one-way data flow, and why it's considered a core React principle.** ⭐⭐
Data flows down the component tree through props; requests to change that data flow back up through callback props that a child invokes. No component ever reaches sideways or upward to mutate another component's state directly — a child that wants something to change must call a function the parent explicitly gave it. This single constraint makes state changes traceable: for any piece of data displayed anywhere in the tree, you can always find exactly where it "lives" by following props upward to the one place a `useState`/hook call actually created it, and you know the *only* way it can change is through the callbacks that specific owner exposed. Contrast a model where any component could mutate any other's data directly — bugs there require searching the whole app for anywhere that touched the data, instead of one well-defined origin point.

**Q: Container vs. presentational components — what's the difference, and does the distinction still matter with hooks?** ⭐
Container components own state and/or data-fetching and coordinate the components beneath them (`App`); presentational components are pure functions of their props with no state or side effects of their own, just rendering what they're given and reporting events upward via callbacks (`ExpenseItem`, `ExpenseList`, `Summary`). The distinction still matters as a design instinct — most of a well-organized tree should be presentational, with stateful/side-effecting logic concentrated in a small number of places — but hooks have softened exactly *where* that logic lives: in `expense-web`, the real "container logic" (state, fetching, loading/error handling) isn't written directly in `App`'s body at all, it's factored into the `useExpenses` custom hook, which `App` simply calls. So it's less "which component is the container" and more "which hook owns the state," but the underlying goal — isolate stateful complexity, keep the rest pure and trivially testable — is unchanged.

**Q: What is the `children` prop, and what problem does it solve?**
`children` is whatever JSX is nested between a component's opening and closing tags, automatically available inside that component as `props.children`. It enables a wrapper component (a `Card`, `Modal`, `Layout`) to control structural chrome — borders, padding, a title, positioning — around *arbitrary* content it doesn't need to know the shape of, rather than trying to anticipate every possible use case through a long list of specific props. This is "composition over configuration": instead of `Card` needing a `bodyText` prop, an `icon` prop, a `footerButtons` prop, and so on to cover every use case, it just accepts `children` and lets the caller supply whatever JSX fits.

**Q: What is prop drilling, and how do you avoid it?** ⭐
Prop drilling is passing a prop through several intermediate components that don't actually use it themselves, purely so it can reach a component several levels deeper that does. It's avoided in a few ways: Context (`useContext`, Phase 4) for data many distant components need without threading it through every layer, a state-management library for complex shared/frequently-changing state (Phase 7), or sometimes simply restructuring the component tree so the data-owning component renders the consumer more directly (passing the consumer itself as `children`/a prop, rather than passing raw data down through layers that then render the consumer).

**Q: What are render props and Higher-Order Components (HOCs), and are they still used?**
A render prop is a function passed as a prop that returns JSX — the parent using the component controls exactly *how* something renders, while the component itself controls *when*/*with what data* to call that function. An HOC is a function that takes a component and returns a new, enhanced component wrapping it (`withAuth(MyComponent)`). Both were the primary ways to share *behavior* between components before Hooks existed, because class components had no other mechanism for reusable stateful logic. Custom hooks (Phase 4) have almost entirely replaced them for *logic* sharing — a custom hook is more direct (no extra wrapper component in the tree, no "wrapper hell" from stacking several HOCs) — but render props/slots still show up specifically for flexible *UI composition*, where you genuinely want the parent to control rendering output, not just share logic.

**Q: How local should component state be, and what's the trade-off?**
As local as possible — colocate state with the component that actually uses it, and lift it only when it's genuinely needed by more than one component. `ExpenseForm`'s field state (`description`, `amount`, `category`, `error`) is a good real example: it stays entirely local to the form, because no sibling needs to know what's currently typed before it's submitted — only the final, validated result crosses the component boundary via `onAdd`. The trade-off: over-lifting concentrates state (and the re-renders it causes) at the top of the tree for data that was never actually shared, while under-lifting (keeping truly-shared data duplicated locally in multiple components) causes the data to drift out of sync, since there's no single source of truth. The right amount of lifting is determined by where the data is actually *needed*, not by convenience or habit.

**Q: How would you structure a medium-sized React app, based on the patterns in this codebase?**
Feature-based folders (`components/`, `hooks/`, `api/` — mirroring `expense-web`'s own layout), the bulk of components written as presentational/pure-function-of-props components, stateful and side-effecting logic factored into custom hooks (like `useExpenses`) rather than scattered across component bodies, a thin container/route layer at the top that wires hooks to presentational components, a small shared UI kit for cross-cutting primitives (buttons, cards, form fields), and a dedicated API layer (plain functions like `expenseApi`, or a data-fetching library like React Query) isolating network calls from components. Keep state local by default and lift only genuinely-shared state; reach for Context or a state library only once prop drilling or cross-cutting frequently-changing state actually becomes a problem, not preemptively.

*Follow-up: where would routing fit into this structure?* React Router (Phase 6) would add a route-level layer above the containers — each route renders a container component for that page, which in turn calls its hooks and composes presentational children, following the same pattern already established for the single-page `expense-web` app.
