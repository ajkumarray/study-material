# Phase 4 — Hooks: Interview Q&A

⭐ = asked constantly.

**Q: What are the Rules of Hooks, and specifically why does calling order matter?** ⭐⭐
The two rules: call Hooks only at the top level (never inside conditions, loops, or nested functions), and only from React function components or other custom Hooks. The reason calling order matters is mechanical: React does not identify each `useState`/`useEffect`/etc. call by name — it identifies each one by *the position it's called in*, per component instance, using an internal ordered list of "hook slots." On a component's first render, React records state for slot 0, slot 1, slot 2, in whatever order the Hooks were called. On every later render, it expects the *same* Hooks to be called in the *same* order, so it can correctly hand back "slot 1's state" to the second `useState` call. If a Hook call is conditional — say, a `useState` only runs when some `if` is true — then on a render where that condition differs, the number and order of Hook calls shifts, and React either hands back the wrong state for a later Hook or throws an error outright, because its slot-based bookkeeping no longer lines up with the calls actually made. The ESLint plugin `eslint-plugin-react-hooks` statically enforces both rules so this class of bug is usually caught before runtime.

**Q: `useMemo` vs `useCallback` — what's the actual difference?** ⭐⭐
`useMemo(computeFn, deps)` caches the *return value* of `computeFn`, recomputing only when a dependency changes; `useCallback(fn, deps)` caches the function *reference itself* and is precisely equivalent to `useMemo(() => fn, deps)` — in other words `useCallback` is `useMemo` specialized for the case where the "value" you want to memoize happens to be a function. Use `useMemo` for expensive derived data, like `Summary`'s `total`/`byCategory` computed via `.reduce()` over the expense list. Use `useCallback` when a function's *identity* matters downstream — passed to a `React.memo`-wrapped child (so the child doesn't see "a new prop" every render and re-render unnecessarily) or listed as a dependency of another `useEffect`/`useMemo` (so that effect doesn't re-run every render just because a fresh function object was created). `useExpenses` wraps `add` and `remove` in `useCallback` specifically so consumers like `App` — and anything `App` passes them to — see a stable reference across renders rather than a new function every time.

*Follow-up: if you remove `useCallback` from `add` in `useExpenses`, what actually breaks?* Nothing about correctness — `add` would still work identically. What changes is that `add` becomes a new function reference on every render of whatever component calls `useExpenses`, which would defeat `React.memo` on any child receiving it as a prop (that child would re-render every time, since one of its props "changed" by reference) and would force any effect listing `add` as a dependency to re-run every render. In `expense-web` specifically, since nothing currently wraps `ExpenseForm` in `React.memo`, removing it wouldn't currently cause a visible bug — but it would silently reintroduce one the moment such memoization was added later, which is exactly why the codebase establishes the habit at the hook boundary.

**Q: What is `useRef` for, and how is it different from `useState`?** ⭐
`useRef(initial)` returns a stable object, `{ current: initial }`, that persists across every render of the component — but critically, **mutating `ref.current` does not trigger a re-render**, unlike calling a `useState` setter. It has two common uses: holding a reference to a real DOM node (via `ref={someRef}` on JSX, then reading `someRef.current` after commit to call imperative browser APIs like `.focus()`), and holding a mutable value that needs to survive across renders but should never itself cause a re-render — a timer id you'll later pass to `clearInterval`, the previous value of a prop for comparison, or an in-flight-request flag. The core distinction from `useState`: state is for anything that should affect what gets rendered; a ref is for bookkeeping that shouldn't.

**Q: `useState` vs `useReducer` — when do you reach for a reducer?** ⭐
`useState` suits independent pieces of state that don't need coordinated updates — exactly `ExpenseForm`'s situation, where `description`, `amount`, `category`, and `error` are four separate, mostly-independent `useState` calls. `useReducer(reducer, initialState)` suits state where transitions are complex, coupled (several fields need to change together, or in a way that's easy to get subtly wrong across multiple scattered setters), or where you specifically want the "how state changes" logic to be a pure, independently unit-testable function separate from rendering and event-wiring code. It's the same `(state, action) => newState` pattern Redux popularized, now available locally per component (or per custom hook) without pulling in a whole library. It scales better than many `useState` calls as the number of related transitions grows, at the cost of more upfront structure — which is exactly why the real `ExpenseForm` doesn't use one; its state is simple enough that a reducer would be unnecessary ceremony.

**Q: What is a custom hook, and why does it need to start with `use`?** ⭐⭐
A custom hook is a function, conventionally named starting with `use`, that composes other Hooks (built-in or custom) to package reusable *stateful* logic that any component can call — the direct analogue of extracting a reusable plain function, but for logic that needs `useState`/`useEffect`/etc. internally. `useExpenses` is the canonical example here: it bundles the expense list's state, loading/error tracking, and the memoized `add`/`remove` operations into one function, so `App` stays a thin renderer that just destructures the hook's return value. The `use` prefix isn't purely a documentation convention — `eslint-plugin-react-hooks` specifically looks for it to know which functions it should apply the Rules of Hooks to; a function that calls `useState` internally but isn't named `useSomething` won't be linted for Hook-rule violations, and other developers won't know at a glance that it carries Hook-like calling constraints (can't be called conditionally, etc.).

*Follow-up: if two different components both call `useExpenses()`, do they share the same expense list?* No — each call creates its own completely independent instance of the internal `useState`/`useEffect` state. A custom hook shares reusable *logic*, not automatically the underlying data. If two components genuinely need to share the *same* state, that requires lifting the state to a common parent (Phase 5) or Context, with only one component actually calling the hook and passing the result down (or up through a Provider).

**Q: Does `useMemo` guarantee the computation won't re-run if the dependencies are unchanged?**
No — it's explicitly a performance hint, not a semantic guarantee. React documents that it may discard a memoized value and recompute it even when dependencies haven't changed, for its own internal memory-management reasons. This means you should never rely on `useMemo` (or `useCallback`) for something that must only execute once, or for a required side effect — only use them to avoid *redundant* work that would produce an identical result if it did re-run. A required side effect belongs in `useEffect`, which has well-defined re-run semantics tied strictly to its dependency array, not `useMemo`'s best-effort caching.

**Q: When should you *not* use `useMemo`/`useCallback`?** *nuance*
When the computation is cheap, or the component simply doesn't re-render often enough for the saved work to matter — the memoization machinery itself (storing the dependency array, comparing it on every render, storing the cached result) has a real, if small, cost, and for a trivial computation that cost can exceed just redoing the work. The React team's own general guidance is to add these hooks in response to a *measured* problem (using the React DevTools Profiler, Phase 7) rather than defensively wrapping every value and function — premature memoization adds code and cognitive overhead without a proven benefit, the same YAGNI instinct that applies to any other optimization.

**Q: What is `useContext`, and what problem does it solve?**
`useContext(SomeContext)` reads the value provided by the nearest `<SomeContext.Provider value={...}>` above the calling component in the tree — without that value needing to be passed as a prop through every intermediate component that doesn't actually use it itself ("prop drilling"). It's well suited to low-frequency, broadly-needed data like the current authenticated user, theme, or locale. Its main limitation is that *every* component consuming a given context re-renders whenever that context's `value` changes, regardless of whether the specific piece of data that component reads actually changed — which makes it a poor fit for high-frequency state (something updating on every keystroke or every second) shared across many components; a dedicated state library with more granular subscriptions (Zustand, Redux with selectors) usually scales better there (Phase 7).

**Q: How would you decide between `useState`, `useReducer`, `useRef`, `useMemo`/`useCallback`, Context, and a custom hook for a given piece of logic?**
Start from what the value actually *is*: if it needs to affect what renders, it's state — `useState` for independent, simple transitions, `useReducer` once transitions get complex or coupled. If it's a side effect synchronizing with something outside React, that's `useEffect`. If it's a value derived from other state/props, compute it during render, wrapping in `useMemo` only if that computation is genuinely expensive. If a function's *reference* needs to stay stable for a memoized child or another Hook's dependency array, wrap it in `useCallback`. If it's a DOM node or a value that must persist across renders but shouldn't itself trigger one, that's `useRef`. If several distant components need the same data without threading it through every layer as props, that's Context. And if a chunk of stateful logic (state + effects + derived callbacks together) is reusable across more than one component — or even just deserves to be pulled out of a component for clarity/testability, as `useExpenses` is pulled out of `App` — that's a custom hook.
