# Phase 7 — Ecosystem & Production: Interview Q&A

⭐ = asked constantly.

**Q: How do you test React components, and what stack does this repo use?** ⭐⭐
With a test runner — here, **Vitest**, a fast Vite-native runner with a Jest-compatible `describe`/`it`/`expect` API — combined with **React Testing Library (RTL)** for rendering and querying components, running in **jsdom** (a fake DOM implementation in Node, so no real browser is needed). You render a real component tree, query elements the way a user would (by accessible role, label, or visible text), simulate real interactions with `userEvent` (typing, clicking), and assert on what's now in the rendered DOM. Crucially, you mock at the *network boundary*, not the components themselves — `App.test.jsx` injects a hand-rolled in-memory fake implementing the same `list`/`create`/`remove` shape as the real `expenseApi`, so every real component and the real `useExpenses` hook execute exactly as in production, with no actual network call.

**Q: What is React Testing Library's philosophy, and why does it query by role/label instead of, say, CSS selectors or component internals?** ⭐
"Test your components the way users actually use them." You query by what's visible and accessible — role (`getByRole('button', { name: 'Add' })`), label (`getByLabelText('description')`), or visible text — rather than by implementation details like CSS class names, internal state, or component instance methods. Two benefits follow directly: tests stay resilient to internal refactors (rewriting `ExpenseForm`'s four `useState` calls as a `useReducer` wouldn't break a single RTL test, since the test never touched that internal detail), and preferring role/label queries nudges you toward writing genuinely accessible markup, since a component that's hard to find by role/label in a test is usually also hard for a screen reader user to operate.

**Q: What's the difference between `getBy*`, `queryBy*`, and `findBy*`, and when do you use each?** ⭐
`getBy*` is synchronous and throws immediately if no matching element exists — use it for elements you expect to already be present. `queryBy*` is also synchronous but returns `null` instead of throwing when nothing matches — its specific purpose is asserting **absence** (`expect(screen.queryByText('bad')).not.toBeInTheDocument()`), because `getBy*` would throw before your assertion even ran. `findBy*` is asynchronous — it returns a Promise that resolves once a matching element appears (or rejects on timeout) — used for content that appears only *after* an async effect resolves, like `await screen.findByText('groceries')` waiting for `useExpenses`'s mount-time fetch to complete before the list is actually in the DOM.

**Q: Why mock the API loader instead of mocking individual hooks or components in tests?**
Because `useExpenses(loader = expenseApi)` is written to accept its dependency as a parameter rather than importing and calling `expenseApi` directly inside itself, tests can pass an entirely in-memory fake object implementing the same shape (`list`/`create`/`remove`) without touching a single line of `useExpenses`, `App`, or any other real component. This means the test exercises the *actual* integration between every real piece — the real hook's state machine, the real form's validation, the real list's rendering, the real delete flow — with only the true external boundary (the network) faked out. Mocking closer to individual components/hooks instead would mean the test verifies less of the real system and is more likely to keep passing even if the real integration between pieces is broken. This is the same Dependency Inversion idea from Software Design Phase 2 (program to an interface/shape the dependency must satisfy, inject the concrete implementation) applied to a React hook.

**Q: When do you need a state-management library beyond `useState`/`useReducer`/Context?** ⭐⭐
When state is genuinely shared across many distant parts of the tree *and* changes frequently enough that Context's "every consumer re-renders on any change" behavior becomes a real performance problem, or when prop drilling/lifting has become unmanageable. At that point: Redux Toolkit for large apps needing a single predictable store with strong devtools (time-travel debugging) and willing to accept more structure/ceremony; Zustand or Jotai for a lighter-weight store with hooks-first ergonomics and fine-grained subscriptions (a component only re-renders for the specific slice of the store it reads). But the first question to ask is usually *what kind* of state this actually is — a large fraction of what looks like "the app needs global state management" is really server data that should be handled by React Query/SWR instead (see next question), not client UI state at all.

**Q: What's the difference between server state and UI state, and why does conflating them cause problems?** ⭐
Server state is data that's actually owned by a backend and merely cached on the client — a list of expenses, a user profile, anything from an API. UI state is purely client-side interface state that has no backend representation of its own — whether a modal is open, which tab is selected, the current (not-yet-submitted) value of a form field. `expense-web`'s expense list is server state (owned by the Spring Boot API, fetched and cached client-side by `useExpenses`); `ExpenseForm`'s in-progress `description`/`amount`/`category` values are UI state (they exist only until submit, and the server never sees them mid-typing). The reason the distinction matters: server state has fundamentally different needs — caching, refetching on staleness, deduplication across components asking for the same data, retry on failure — that a purpose-built library (React Query/SWR) handles well and a general client-state store (Redux/Zustand) does not, out of the box. Conflating the two — manually caching API responses inside a Redux store, say, instead of using a data-fetching library purpose-built for that job — is where a lot of unnecessary state-management complexity in real production apps actually originates.

**Q: When does a component re-render, and what are the tools to optimize it?** ⭐
A component re-renders when its own state changes, when its props change, or — a detail beginners often miss — **whenever its parent re-renders, even if this component's own props are unchanged**, unless it's explicitly wrapped in `React.memo`. To optimize a *measured* hotspot (found with the React DevTools Profiler, not guessed at): `React.memo` skips a component's re-render if its props are shallowly equal to last time; `useMemo`/`useCallback` (Phase 4) keep computed values/function references stable across renders so they don't spuriously defeat a child's `React.memo` or force an effect to re-run; and correct, stable `key`s (Phase 2) let the reconciler reuse unchanged list items' DOM subtrees instead of recreating them. None of these should be applied by default across a whole tree — they each add real cost (extra comparisons, extra memory) and are worth it only where profiling shows an actual problem.

**Q: What is `React.memo`, and why is it easy to accidentally defeat?**
It's a higher-order component wrapping another component so React skips re-rendering it when its props are shallowly equal (`===`, one level deep) to the previous render's props. It's easy to defeat because an inline function or object literal passed as a prop — `onClick={() => remove(id)}`, or `style={{ color: 'red' }}` — is a *brand-new reference* every render of the parent, so the shallow comparison sees "changed" every single time regardless of memoization. This is exactly why `useCallback` matters specifically at this boundary: in `useExpenses`, `add` and `remove` are wrapped in `useCallback` precisely so that if `ExpenseForm`/`ExpenseItem` were later wrapped in `React.memo`, they'd actually see a stable `onAdd`/`onDelete` reference across renders and the memoization would actually take effect — without that, `React.memo` would be silently doing nothing useful.

**Q: How is a React app built and deployed, based on how `expense-web` is set up?** ⭐
Vite bundles the app with `npm run build` into static HTML, CSS, and hashed JS files in `dist/` — this is verified to actually work in this repo. Because the output is just static files (all rendering logic runs client-side in the browser — this is a CSR/client-side-rendered app), it can be deployed to literally any static host or CDN — Netlify, Vercel, S3+CloudFront — with no dedicated application server required for the frontend at all. Environment-specific configuration, like the backend API's URL, is injected via `VITE_`-prefixed environment variables read through `import.meta.env` (`const BASE = import.meta.env.VITE_API_URL ?? 'http://localhost:8080'` in `expenseApi.js`) rather than hardcoded, so the same built artifact can point at different backends per environment without a rebuild.

**Q: How does a React SPA fit into a full-stack system, concretely for this repo?**
The React SPA (static files served from a CDN) runs entirely in the browser and calls a separate backend REST API — the Spring Boot `expense-api` (track 02) — over HTTP, attaching a JWT (issued by Spring Security, Spring Boot Phase 7) to authenticate requests; the API in turn talks to Postgres (track 04) for actual data storage and enforces authorization server-side. The React app never validates the JWT itself or talks to the database directly — it only stores the token (in memory, `localStorage`, or a cookie) and attaches it to outgoing requests; the backend is the sole authority on whether a request is actually allowed. Next.js (track 09) would add server-side rendering on top of this same component model, primarily for cases where CSR's weaker SEO and blank-then-populate first paint actually matter for the app.

**Q: What's the difference between CSR, SSR, and SSG, and where does `expense-web` sit?**
CSR (client-side rendering — what `expense-web` does, via plain Vite/React) ships an essentially empty HTML shell plus a JS bundle; the browser downloads and runs the JS, which then renders everything — fast subsequent navigations (no full reloads, per Phase 6), but a slower/blank-then-populated first paint and weaker SEO, since a crawler that doesn't execute JS sees an empty page initially. SSR (server-side rendering) renders the actual HTML on the server for each request, so the first paint already has real content — better SEO and perceived load time, at the cost of a server doing work per request. SSG (static site generation) renders the HTML once at *build* time rather than per request, serving pre-built HTML from a CDN — fastest possible delivery for content that doesn't change per-request, but not suited to highly dynamic, per-user data. Next.js (track 09) provides SSR and SSG (and hybrid approaches) as first-class options on top of the same React component model this whole track has been building — `expense-web` itself is a pure CSR app, which is the right choice for an authenticated, highly interactive internal tool where SEO doesn't matter and the loading-state trade-off is acceptable.
