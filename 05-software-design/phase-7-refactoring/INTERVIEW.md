# Phase 7 — Refactoring & Code Smells: Interview Q&A

⭐ = asked constantly.

**Q: What is refactoring?** ⭐⭐
Changing code's internal structure without changing its external, observable behavior — the goal is improved readability, reduced complexity, and easier future change, with the *exact same* functionality before and after. It's done in small, safe, test-backed steps, never as a wholesale rewrite: make one small structural change, re-run the tests, confirm they're still green, commit, repeat. `Refactoring.java` demonstrates this concretely — every refactored method has an assertion of the form `before(...) == after(...)` proving the structural change didn't alter the result.

*Follow-up: "How is refactoring different from a rewrite?"* A rewrite discards the existing implementation and starts over, usually changing behavior along the way (intentionally or not) and losing the incremental safety net of "small step, verify, small step, verify." Refactoring is deliberately incremental and behavior-preserving at every single step — you could stop after any individual step and still have a fully working system.

**Q: What is a code smell? Give examples.** ⭐⭐
A surface symptom pointing at a deeper design problem — not a bug (the code still behaves correctly), but a strong signal that it will be hard to change safely. Examples: long method (does too much, at mixed levels of abstraction), god/large class (bundles unrelated responsibilities — the Phase 2 SRP violation), duplicated code (the worst one, since duplicated logic drifts out of sync when only one copy gets updated), long parameter list (often several parameters that are really one concept), feature envy (a method more interested in another class's data than its own), switch-on-type (a conditional that must grow with every new case), primitive obsession (a bare `String`/`double` standing in for a concept that deserves its own type), shotgun surgery (one conceptual change forces edits scattered across many unrelated places), and anemic domain (data with no behavior, logic living elsewhere). Smells tell you *where* to look for a refactor, not that a refactor is automatically required — a three-case `switch` that will realistically never grow a fourth case may not be worth "fixing."

**Q: How do you refactor a long method / a god class?**
A long method → **Extract Method**: pull named, single-purpose sub-steps out of it, so each piece is independently readable and independently testable — `receiptTotal_before` (line-total calculation and a magic-number discount, all inline) becomes `subtotal(items)` plus `applyBulkDiscount(amount)`, each with a clear name and, in the discount case, named constants replacing the bare `500`/`0.9`. A god class → **Extract Class**, splitting by responsibility toward SRP, combined with **Move Method/Field** to relocate behavior and data to the class that actually owns them. Either way, the discipline is the same: do it in small steps, running the full test suite after each one, so behavior is provably preserved throughout rather than just hoped to be.

```java
static double subtotal(List<Item> items) { return items.stream().mapToDouble(i -> i.qty() * i.price()).sum(); }
static double applyBulkDiscount(double amount) { return amount > BULK_THRESHOLD ? amount * (1 - BULK_DISCOUNT) : amount; }
```

**Q: What is "replace conditional with polymorphism"?** ⭐⭐
Turning a type-switch (`switch (type) { case "standard": ...; case "express": ...; }`) into a set of strategies — one per case — selected once and then dispatched polymorphically rather than re-checked on every call. In `Refactoring.java`, `shippingCost_before` switches on a `type` string directly inside the cost calculation; `shippingCost_after` instead asks a factory method, `shippingFor(type)`, for the right `Shipping` strategy exactly once, then calls `.cost(weight)` on it with no conditional at all in the calculation logic itself. Adding a new shipping type afterward means adding one case inside `shippingFor` — the calculation code, and anything else that already consumes a `Shipping`, never changes again. This is the mechanical fix for a switch-on-type smell, and it's a direct, concrete application of Open/Closed (Phase 2) together with the Strategy pattern (Phase 5).

*Follow-up: "Doesn't the switch still exist somewhere?"* Yes — the type-to-behavior decision has to be made *somewhere*, and Replace Conditional with Polymorphism doesn't eliminate that decision entirely; it centralizes it into exactly one place (a factory method, Phase 3) so that every other piece of logic that needs shipping-cost behavior is entirely conditional-free and doesn't need to change when a new type is added.

**Q: How do you refactor safely?** ⭐⭐
Have tests first — write them before refactoring if they don't already exist, since without a test suite "refactoring" is really just editing code and hoping. Make exactly one small structural change at a time. Run the tests immediately, and they must stay green. Commit that one change, then repeat. Critically, never mix a refactor with a feature change in the same step — if you change structure *and* behavior together and a test then fails, you have no way to know which of the two changes actually caused it, whereas one-change-at-a-time isolates the cause immediately, by construction.

**Q: What is TDD and how does it help design?** ⭐
Test-Driven Development follows Red (write a failing test describing behavior that doesn't exist yet) → Green (write the simplest possible code that makes it pass, no more) → Refactor (clean up the implementation while the tests you just wrote stay green throughout). It drives small, focused, testable units almost as a natural side effect of writing the test first, and it gives you the refactoring safety net from the very first line of a feature rather than retrofitting tests onto code after the fact. Writing the test first also surfaces design problems early: if a test is awkward to write (you need to construct five unrelated collaborators just to test one calculation), that awkwardness is usually telling you the *design*, not the test, needs work.

**Q: Why is untestable code considered a design smell in itself?**
Because difficulty testing a piece of code almost always traces back to the same handful of underlying problems that also make the code hard to *change* safely: tight coupling to concrete dependencies (a hard-coded `new EmailSender()` instead of an injected `MessageSender` interface, Phase 2's DIP), hidden dependencies reached through a global Singleton instead of passed in explicitly (Phase 3), or a class doing too many unrelated things at once so testing one behavior drags in setup for several others (an SRP violation, Phase 2). Improving testability — injecting a dependency instead of constructing it internally, splitting a class along its actual responsibilities — is very often identical to improving the design, not a separate, unrelated task bolted on afterward. This is why "hard to test" is one of the fastest, most reliable red flags a reviewer can use to spot a deeper SOLID or coupling problem.

**Q: What is technical debt and how do you manage it?** ⭐
The implied future cost of a shortcut, whether deliberately chosen (ship now, accept a known trade-off) or accidentally accumulated (cruft nobody explicitly decided to take on). Like financial debt, some of it can be a genuinely reasonable strategic choice, but unpaid "interest" — changes that get slower over time, bugs clustering around the affected code, harder onboarding for new engineers touching it — compounds the longer it's left unaddressed. Manage it by making it visible rather than letting it quietly become invisible (track it explicitly, don't just tolerate it silently), and pay it down continuously through the Boy Scout Rule and regular, test-guarded refactoring — rather than pinning hopes on a dedicated "cleanup sprint" that, in practice, competing priorities usually keep pushing indefinitely.

**Q: When should you NOT apply a principle or pattern?** *nuance*
When applying it adds complexity without relieving any real, present pain — a needless layer of abstraction, a factory built for a single implementation that will realistically never gain a second, or force-merging two blocks of code that are only coincidentally similar in the name of DRY (which then wrongly couples two concepts that should be free to evolve independently). SOLID and the GoF patterns exist to serve readability and changeability; over-applying them past that point creates its own flavor of technical debt — complexity that exists purely for the pattern's own sake. Keep it simple (KISS/YAGNI, Phase 1) until a concrete, present complexity actually justifies the investment. This is judgment, not dogma, and it's exactly the kind of nuance senior-level interviews probe for.

**Q: What do you look for in a code review?**
Correctness first, but well beyond it: readability, design quality (SRP adherence, coupling, any of the named smells from this phase), test coverage — especially of the actual behavior change, not just line coverage — naming, error handling (does it fail loudly and close to the cause, per Phase 1), and consistency with the rest of the codebase, plus the usual security and edge-case sweep. Give feedback that's specific and actionable rather than vague ("this method mixes two concerns — consider extracting the validation into its own method" beats "this feels messy"), stay kind and focused on the code rather than the person, and treat review as a mechanism for spreading design knowledge and conventions across the team, not merely a correctness gate before merge.

**Q: If you found a long method with a switch-on-type buried inside it, which would you fix first — the long method or the switch?**
Extract the switch-on-type block out on its own first (Extract Method), which both shortens the long method immediately *and* isolates the type-dispatch logic into a single, clearly-named place you can then decide whether to further refactor with Replace Conditional with Polymorphism. Tackling both smells in one giant restructuring step makes it much harder to tell, if a test breaks, which specific change caused it — exactly the "one small step, verify, then the next step" discipline this phase is built around. In practice: Extract Method first (cheap, safe, immediately useful), then evaluate afterward whether the now-isolated switch is *actually* going to grow enough new cases over time to justify the added ceremony of Replace Conditional with Polymorphism, rather than applying it reflexively to every switch you ever see.
